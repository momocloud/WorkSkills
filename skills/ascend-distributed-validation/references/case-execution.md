# 用例执行与证据

## 确定入口，而不是选择惯用命令

结合当前用户请求、项目说明、仓库已有运行配置和源码确认：

- **启动层级**：入口是否已经 spawn/fork 子进程，是否依赖测试框架、构建产物、外部 launcher 或集群调度。测试文件不一定可以直接执行。
- **资源拓扑**：单/多进程、单/多节点、卡数和设备映射；rank/world size 的来源；会合地址、端口是否由入口硬编码或通过参数传入。不要擅自将多机用例缩成单机后标为同等覆盖。
- **工作负载**：尺寸含义是元素数、每 rank 输入、每 peer 分片还是总输出；dtype、归约类型、迭代、预热及通信域/内存池生命周期。不能把不同脚本的同名 shape 参数当作相同字节数。
- **判据和产物**：断言、返回码、结果文件、只打印的错误、SKIP 条件、日志生成时机，以及异常是否会向父进程传播。不要默认所有脚本都会输出 CSV。

依据这些事实组成命令。批跑可以按各入口分别执行，不要求统一 CLI、固定串行/并行策略或套用同一个 wrapper。并发是否合适取决于用例资源隔离与测量目标；共享设备上的性能比较应记录可能的干扰。

用户给出的“全量”按当前目录入口、项目矩阵或明确需求清点，不等于穷举所有可配置参数。区分测试入口、辅助模块和会修改源码/状态的维护工具。只有实质影响范围且已有材料无法判断时才澄清，不重复确认已经明确授权的用例。

## 运行与中断

沿用用户选定的环境；记录实际解释器、框架包、CANN/驱动及源码提交或文件哈希。按排查需要核对加载库路径和制品哈希，不能仅凭版本号断言两套环境完全一致。

使用设备前检查健康与占用；协调当前用例的设备、端口和节点资源。设备空闲记录不是预留。不为解决冲突停止其他任务、重置设备或修改系统环境。

超时依据用例预期耗时、通信超时和故障设计设置，不能照搬一次实验的固定秒数。记录启动、业务输出和退出收尾时间；启动/收尾耗时不是通信延迟。

如果原程序在 worker 失败后继续等待队列，先核实子进程状态、首个异常与预期收尾逻辑。只有确有必要时，才按唯一任务标记、进程组或调度器作业 ID 清理已确认属于本次运行的资源。不要按 `python` 进程名或仅按同账号批量终止。

为长任务保留实际命令、状态和独立输出目录。断点续跑前核对环境、源码、参数及已完成前缀；已经完成的项不重复覆盖。VPN/SSH 断开时先查远端任务是否仍在运行，不直接重新提交整批。

## 结果对照

比较相同入口、参数、源码及判据；这些条件不齐时，明确只比较错误类型或完成情况。逐项列出一致、不同、未覆盖、证据不足，不能把另一份报告未提及的用例视为通过。

因前一个模式失败而没有执行后续模式时，将后续模式记为未执行。任务要求覆盖且支持独立启动时可另行补跑，并记录两次命令，不能修改旧记录制造“全部执行”的结果。

追查变量影响时区分一次改变一项的对照与整组诊断配置。性能日志、异步错误处理和执行模式变化都可能影响行为；诊断运行的耗时不能直接替代正常配置下的性能结论。
