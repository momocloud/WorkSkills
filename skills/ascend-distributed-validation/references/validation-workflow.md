# 验证需求流程

本流程连接需求、用例、证据和结论，不规定用例执行命令，也不要求每个任务依次经过所有阶段。只有已有日志时可直接分析；环境已就绪时无需重复安装；用户只要某一轮报告时，不自动扩展成修复和回归任务。

## 1. 明确本轮要证明什么

先读原始需求、已有用例、执行说明和现有记录，区分目标：验收某项能力、按目录跑一遍、复现指定命令、对齐另一环境、分析现有结果或替协作方补采日志。输出应回答当前目标，不能用“程序能启动”替代能力验证，也不能用目录覆盖声称整个需求已验收。

沿用当前会话已明确的范围、环境和分工。用户自行执行时提供分步命令并核对回传；用户授权 agent 执行时继续完成相应工作，不在每个阶段重复索要确认。只对会影响结论且无法从现有材料确定的信息提问。

用户途中补充版本、用例或日志要求时，更新本轮计划与待办；保留此前轮次的条件和证据。除非用户明确替换任务，不因一个定位问题丢失原来的验证目标。

## 2. 建立需求到证据的对应关系

为复杂任务维护一份轻量覆盖表，可沿用项目已有格式，不要求创建固定文件或使用统一 schema。按需要记录：

| 内容 | 要解决的问题 |
| --- | --- |
| 需求点及来源 | 当前结论针对哪项行为或约束？ |
| 用例、模式和场景 | 哪个入口能覆盖它，哪些仍没有用例？ |
| 验收判据 | 看断言、误差、行为、性能指标还是资源趋势？ |
| 前置条件 | 需要什么环境、拓扑、设备、依赖或数据？ |
| 本轮范围与结果 | 计划执行、实际完成、跳过、阻塞还是尚未覆盖？ |
| 证据位置 | 哪轮命令、源码和日志支持这一结论？ |

覆盖维度来自需求与实现，例如算子、dtype、尺寸、通信域、生命周期或故障场景；不要照搬旧项目的矩阵。区分目录入口覆盖、有效参数组合覆盖和需求覆盖。原脚本过滤掉的组合与执行异常后缺失的组合分别统计。

清点脚本时辨识辅助工具；文档里的命令可能包含断行、拼接错误或过时参数。核对当前入口再整理，保留原命令与必要调整的理由。具体执行方式按 [用例执行与证据](case-execution.md) 确定。

缺少脚本、输入或远端副本时，先在已授权来源中查找并按需同步，核对实际执行副本的提交或哈希。不要另写一个看似等价的程序替代原用例，却把结果归入原用例。

## 3. 判断前置条件是否足够

环境就绪检查服务于本轮验证。包安装、导入、设备可见、通信可用和需求行为是不同层级；只做当前任务需要的检查。已有可信且仍适用的检查可以复用，设备占用等动态状态需要重新核实。

如果环境未知或多个入口共用脆弱前置条件，可以先用合适的代表性检查暴露共同问题。其启动方式、资源规模和判据仍由具体用例决定；不固定为单卡/双卡冒烟，不因此缩减已要求的全量范围。已有条件充分时直接执行计划，避免机械地重跑检查。

“与另一环境一致”先列出已知版本、制品来源、实际加载库、源码和硬件/驱动条件，再标明未知项。下载页、产品发行号、包版本、构建时间与制品哈希不是同一件事；核实差异再决定是否需要切换。不要因两个报告结果不同就反复安装版本号相同的包。

需要准备或切换环境时，遵循当前明确的环境选择，按需使用环境管理能力。不会由本技能默认升级到最新版本，也不会由环境安装成功默认启动测试。

## 4. 按计划执行，并依据故障影响推进

运行中保留轮次身份、实际命令、环境覆盖和对应源码；新增模式、补跑或诊断设置使用独立记录。长任务只维护足够恢复工作的最新状态：已完成项、活动项、阻塞原因、下一步和证据位置，不把全部日志重复写进状态文件。

根据影响范围决定后续行动，而不是“失败就全部停止”或“失败也全部继续”：

- 缺包、入口配置错误等共同前置问题影响后续同类用例时，先处理或明确阻塞范围，避免制造大量无意义失败。
- 单个独立用例失败后，保留原错误；确认资源已恢复、后续任务不受影响且仍在授权范围内，可以继续其他项。
- 资源占用、残留进程或设备状态异常时，先核实是否还能安全继续；不能通过终止其他任务或重置共享设备强行推进。
- 本项异常导致后续模式没执行时，记录缺口。任务要求覆盖且入口允许独立启动时补跑，不改写旧运行的完成状态。

通信/收尾超时、断点续跑和清理边界按 [用例执行与证据](case-execution.md) 处理。连接丢失、提交成功、远端退出、证据已取回分别记录；SSH 断开不等于任务停止，文件下载完成也不等于业务通过。

## 5. 从失败现象形成可检验的问题

先按证据区分环境/入口、业务执行、退出清理、预期异常、数值判据、性能指标或资源趋势，再决定下一步。分类不是最终责任归属；同一错误码不等于同一缺陷。

对真正影响结论的不确定性，提出一个有判别力的下一步。复杂定位可用“问题或假设—证据—保持不变的条件—改变项—观察结果—结论限制”记录，简单问题用几句话即可。例如：

- 完整序列失败但单档成功：保留并对照前置通信、分配/释放历史与域生命周期，不能因单档成功就否定原始失败。
- 两个实现同时超过精度阈值：检查参考值、误差界和数据条件；误差相同既不证明都正确，也不证明某一实现独有问题。
- 可用显存下降：区分预热后的持续趋势、分配器统计、设备统计和进程退出后的状态；只看最终差值不足以判泄漏或误报。
- 性能表缺失：先查表格打印时机及异常前的日志，不能推断第一档就失败。

原始失败、最小复现、修正后的用例和诊断实验分别留存。缩小用例时写清改变了什么以及是否仍能触发原现象；最小复现不能替代原范围的结果。额外实验限于当前授权的定位范围，不因猜测就切环境、改代码或扩跑压力/故障场景。

需要 HCCL 深入定位时再按 [HCCL 诊断](hccl-diagnostics.md) 采集，不把大量诊断日志或执行模式开关默认带入每次验证。

## 6. 复测、交接与完成判定

拿到新环境、修复或协作方建议后，说明相对基线改变了哪些条件，并确定相应复测范围。授权范围允许时，可先检查原始失败是否仍复现，再按风险和任务要求扩展；用户明确要求全量重测时完成全量，不能用几个代表用例替代。诊断配置成功不自动等于默认配置已修复。

跨轮比较时同时列出结果一致、结果不同、尚未覆盖和证据不足；版本变更、用例修正、阈值变化和日志开关不混作一个原因。对照记录与原始结果一起保留。

交接按 [结果报告与归档](test-reporting.md) 给出可复现材料和待解释的问题，不要求接手人先读整段会话。结束时分别判断：

- **本轮工作是否完成**：约定范围内的运行/分析已处理，缺口和阻塞写明，结果与证据对应，必要的资源收尾及交付检查完成。未完成的计划项不能标为全量执行完成。
- **需求是否达到验收条件**：依据约定判据与覆盖范围判断，不能由批跑退出成功推导。
- **缺陷是否已经闭环**：只有任务包括修复/回归且具备相应证据时才下此结论。报告或日志采集任务可以完成，同时明确问题尚未解决。

归档、删除旧结果或向外部发送材料按用户要求另行处理，不能作为每次验证的自动收尾动作。
