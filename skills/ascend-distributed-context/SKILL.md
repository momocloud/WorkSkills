# 昇腾分布式工作背景

将以下内容作为理解用户新任务的背景。它是个人工作上下文，不是团队正式规范，也不是某个旧需求的续办清单。当前用户指令和目标仓库规范优先。

## 已确认的身份与范围

- 用户在**华为昇腾计算框架组的分布式小组**工作。
- 用户目前确认的主要仓库是 **torchnpu / torch-npu**，代码中的 Python 包名为 `torch_npu`。这不是完整仓库清单，不推断其他仓库的归属或用户职责。
- 讨论需求时，优先从昇腾 NPU 上的框架分布式支持、上游行为对齐、适配与验证角度理解；具体工作可能是开发、排障、测试或审查，不默认每次都是补测试。

## 技术语境与仓库辨识

以下是历史工作涉及的相关领域，用于快速定位，不代表小组对所有模块拥有维护责任：

| 方向 | 定位线索 |
| --- | --- |
| 通信与进程组 | `torch.distributed`、c10d、ProcessGroup、HCCL、集合通信与 P2P |
| 分布式训练与张量布局 | DDP、FSDP、DTensor、DeviceMesh、张量并行、通信 hook |
| 配套能力 | distributed checkpoint、启动与 rendezvous、elastic、分布式工具接口 |

区分三个对象：PyTorch 上游实现、torch-npu 仓库的适配代码及测试、实际运行环境中安装的包。它们的分支和提交可能不同。

- 不根据目录名 `pytorch` 判断它是上游 PyTorch：先看 Git remote、包结构及仓库说明。用户 fork 与组织上游也要区分。
- 需要定位行为时，沿目标版本的上游定义、torch-npu 适配/补丁、实际调用路径查证。先确认实现归属，再决定修改哪个仓库。
- `test/distributed/`、`torch_npu/distributed/` 可作为查找起点；路径是否存在、内部布局和测试惯例以当前 checkout 为准。
- 接口不存在、路径迁移、静态解析失败、后端不支持是不同问题。不能因旧入口找不到就断言底层能力消失；是否迁移或跳过由当前任务范围决定。

## 从既往工作归纳的协作习惯

这些是默认偏好，遇到当前指令或仓库惯例不同，应相应调整。

- 用中文沟通分析、进展和交付；代码注释倾向简洁英文，减少模板话术，说明必要的意图或限制。
- 先读真实实现和已有测试，再确认缺口。搜索命中只算线索，需要检查调用和断言；优先复用已有覆盖，避免重复维护。
- 明确验证结论的边界：生成、静态检查、实际执行、覆盖充分性分别说明；单进程工具测试、多卡通信验证、mock 场景各自能证明什么要说清。
- 根据需求选择功能、结构、异常、数值或性能验证，不把旧任务的特定测试限制沿用到新任务。
- 多条需求需要追踪时，保留原始输入，另建可追溯的处理记录；将范围处置、覆盖判断和运行结果分开，跳过或待处理不算通过。
- 对需要复现的结果保留对应命令、源码版本、日志和验证范围；存在多份源码时按需核对提交或文件哈希。安装包的测试结果不能冒充当前源码构建后的验证。
- 倾向把任务分析、临时证据与拟合入仓库的代码分开整理。采用当前目录已有组织方式，不强制固定目录名或报告模板。
- 接续较长任务时维护简短的最新状态入口，写清已完成、未完成及证据位置；旧报告保留为历史，不让旧“下一步”覆盖新结论。
- 提交信息和代码风格参考目标仓库及用户给出的格式；旧任务的提交、推送或改写历史授权不自动延续到新任务。

## 新目录的快速导入

1. 读取当前目录已有的 `AGENTS.md`、README 和交接记忆（如存在），了解新任务和目录约定；无需寻找或复制历史任务目录。
2. 将本 skill 中的身份、仓库辨识和协作习惯载入当前上下文。只核实新任务真正依赖的仓库位置、目标分支、实现版本和验收范围，不为导入背景本身要求用户填写清单。
3. 用户要求初始化目录并保存背景时，按现有记忆约定落盘；无约定时在 `MEMORY.md` 中新增或更新“通用工作背景”小节。仅保存上述可复用背景，与当前任务进度分开；保留文件中其他内容，重复调用不重复追加。仅要求了解背景时无需创建文件。
4. 简短说明已导入的背景，然后继续当前任务。机器连接、账号、依赖安装及环境复现不属于本 skill；需要时使用已安装的 `remote-npu-environment`，其缺失不影响背景导入。

后续仅将用户确认的长期事实或明确偏好更新到通用背景。单次需求、接口清单、特定跳过规则、测试数量、提交号、分支、仓库绝对路径及执行状态留在各任务记录；不记录机器地址、账号、卡号、环境版本或安装步骤。
