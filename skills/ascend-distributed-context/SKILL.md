# 昇腾分布式工作背景

将以下内容作为理解用户新任务的背景。它是个人工作上下文，不是团队正式规范，也不是某个旧需求的续办清单。当前用户指令和目标仓库规范优先。

## 已确认的身份与范围

- 用户在**华为昇腾计算框架组的分布式小组**工作。
- 用户目前确认的主要仓库是 **torchnpu / torch-npu**，代码中的 Python 包名为 `torch_npu`。这不是完整仓库清单，不推断其他仓库的归属或用户职责。
- 用户的工作仓库维护在 **GitCode**，需求材料中可能直接引用 GitCode Issue、PR 和源码链接。
- 讨论需求时，优先从昇腾 NPU 上的框架分布式支持、上游行为对齐、适配与验证角度理解；具体工作可能是开发、排障、测试或审查，不默认每次都是补测试。

## 技术语境与仓库辨识

以下是历史工作涉及的相关领域，用于快速定位，不代表小组对所有模块拥有维护责任：

| 方向 | 定位线索 |
| --- | --- |
| 通信与进程组 | `torch.distributed`、c10d、ProcessGroup、HCCL、集合通信与 P2P |
| 分布式训练与张量布局 | DDP、FSDP、DTensor、DeviceMesh、张量并行、通信 hook |
| 配套能力 | distributed checkpoint、启动与 rendezvous、elastic、分布式工具接口 |

区分三个对象：PyTorch 上游实现、torch-npu 仓库的适配代码及测试、实际运行环境中安装的包。它们的分支和提交可能不同。

- 不根据目录名 `pytorch` 判断它是上游 PyTorch：先看 Git remote、包结构及仓库说明。用户 fork 与组织上游也要区分。
- 需要定位行为时，沿目标版本的上游定义、torch-npu 适配/补丁、实际调用路径查证。先确认实现归属，再决定修改哪个仓库。
- `test/distributed/`、`torch_npu/distributed/` 可作为查找起点；路径是否存在、内部布局和测试惯例以当前 checkout 为准。
- 接口不存在、路径迁移、静态解析失败、后端不支持是不同问题。不能因旧入口找不到就断言底层能力消失；是否迁移或跳过由当前任务范围决定。

## GitCode 链接读取

面对 GitCode 链接，可以使用 **OpenAPI + Git** 获取信息，无需以安装 MCP 或专用 CLI 为前提。网页抓取失败不代表资源不可访问。

- **OpenAPI 读取需求与协作信息**：解析链接中的 owner、repo、Issue/PR 编号，读取正文、状态、评论、PR 文件及提交列表。Web 路径中的 `pull/<编号>` 或 `merge_requests/<编号>` 对应 API 的 `pulls/<编号>`。
- API 基址为 `https://api.gitcode.com/api/v5`。常用 GET 路径如下；接口变化时核对官方说明和实际响应：

  | 内容 | API 路径 |
  | --- | --- |
  | Issue 详情 / 评论 | `/repos/{owner}/{repo}/issues/{number}`，其后追加 `/comments` |
  | PR 详情 / 评论 | `/repos/{owner}/{repo}/pulls/{number}`，其后追加 `/comments` |
  | PR 改动文件 / 提交 | `/repos/{owner}/{repo}/pulls/{number}/files`、`/commits` |

- 对公开资源可先匿名读取，已有成功案例，但不保证所有仓库或接口都允许匿名访问。需要认证时使用已授权的 Token；Git SSH 密钥不等于 OpenAPI Token。区分认证失败、权限不足、资源不存在及限流，不将单次失败解释为仓库不存在。Token 不写入技能、报告或日志。
- 评论、文件和提交列表按接口分页规则读取；需要完整上下文时读完各页，不能将第一页当作全部。检查返回类型及字段，不将 HTTP 成功但实际返回 HTML 的响应当作有效 JSON。
- **Git 读取源码与版本差异**：先核对已有 checkout 的 remote；按需 fetch 目标引用，或在独立目录克隆。依据 PR 返回的源/目标仓库与提交 SHA 定位代码，使用 `git show`、`git diff` 等查看完整实现，不用当前分支代替 PR 对应版本。API 的 patch 缺失或截断时，用 Git 补全；保留现有工作区修改。
- 交付时引用原 Issue/PR/源码链接，注明实际读取范围及未获取的部分；读取链接本身不授权发表评论、创建 PR 或推送代码。

## 需求开发流程与分支规范

需求类研发任务遵循「**先写 RFC 并通过评审 → 在独立分支 worktree 上实现与验证 → 按标准模板创建 PR**」的流程。

### 1. RFC 编写与评审（PR 前置）

- 需求开发在进入正式 PR 合入前，先基于 [RFC 模板](references/rfc-template.md) 编写完整 RFC 供评审；经评审确认方案与未决问题后，再基于结论推进或收口 PR。
- 编写 RFC 时先读取 [RFC 模板](references/rfc-template.md)，完整保留其章节结构（概述与非目标、用例分析、总体方案/技术选型/功能与性能/安全隐私与 DFX/编程与调用设计、测试设计、缺点和风险、现有技术、未解决问题、附录）。
- 某子项确不涉及时明确写清“不涉及”及原因，避免静默删节；接口定义尽量补全参数表、返回值表、异常处理、约束说明与调用参考代码。

### 2. 分支与 Worktree 规范（禁止在 fork 的 `master` 直接开发）

- **严禁在个人 fork 仓库的 `master`（主干分支）上直接修改代码或提交**。主 checkout 的 `master` 仅用于保持干净、同步上游基线。
- 每次开展需求开发、缺陷修复或重构时，必须通过 `git worktree` 基于最新目标基线创建**新的独立分支与独立 worktree 目录**，在该 worktree 中完成修改、构建、测试与提交。
- 动手前先检查当前所在目录、分支与 remote（`git status`、`git branch --show-current`、`git remote -v`、`git worktree list`），若当前正处于 `master`，先切出新分支 worktree 再改代码：

  ```bash
  # 先同步上游/基线，再为当前任务创建独立分支的 worktree（按实际 remote、基线分支、目录与分支名替换）
  git worktree add -b <new-branch-name> <worktree-path> <base-ref>
  ```

- 多个并行任务各自使用独立分支和独立 worktree，避免相互污染；任务合入或终止后再按需清理对应 worktree。

### 3. torch-npu 提交前 lint

准备代码提交（包括检视后的补改）时，从该 worktree 的仓库根目录执行目标分支 CI 配置的 lint。torch-npu 使用 `CodeCheck_lintrunner` 时，先用 `lintrunner init` 准备仓库指定的工具版本，再按 `.lintrunner.toml` 对本次 PR 新增和修改的全部文件运行检查。C++ 格式以仓库配置的 clang-format 为准。

提交前先暂存此次准备提交的修改，包括新文件。lintrunner 读取工作区内容，确保待检文件的工作区版本与拟提交版本一致。以下命令覆盖分支上已有的提交和本次暂存改动，`target_ref` 按实际 PR 目标填写：

```bash
(
  set -eo pipefail
  target_ref=upstream/master  # 替换为已更新的目标分支引用
  base=$(git merge-base "$target_ref" HEAD)
  lintrunner init
  git diff --cached --name-only --diff-filter=AM -z "$base" |
    xargs -0 -r lintrunner --
)
```

出现诊断时修复对应文件，检查格式化差异，重新暂存并对完整 PR 范围复跑，确认退出码为 0。复现已有 GitCode CI 失败时，在独立 worktree 检出该次任务的 PR 合并提交（`refs/merge-requests/<PR号>/merge`），使用任务实际比较的目标分支 SHA 与合并提交生成同样的文件清单。PR 中分别记录本地 lint 结果和线上 CI 状态。

### 4. PR 说明与合入检查

- 创建或准备 PR 描述时，先读取 [PR 说明模板](references/pr-template.md)，严格沿用其章节与格式（`【合入来源】`、`【修改方案】`、`【资料变更】`、`【接口变更】`、`【功能验证】`、`【CheckList】`）。
- **脱敏硬要求**：如有社区 Issue 请关联链接；**严禁在 PR 描述中携带任何内部流程信息**（内部需求链接、内部问题单、内部 Issue 等）。
- 需求或重构类 PR 须在 `【修改方案】` 中补充详细设计说明（可提炼已评审通过的 RFC 内容，说明上下游组件关系、时序图/类图、DFX 能力等）；`【资料变更】` 与 `【接口变更】` 不涉及时明确填写“不涉及”。
- `【功能验证】` 如实写明测试场景、测试步骤、UT 看护情况与实际验证证据，不虚构未执行的测试或截图；`【CheckList】` 逐项核实通过或不涉及后再将 `[ ]` 改为 `[x]`，并确认 PR 标题使用规范类型标签（如 `feat`、`fix`、`refactor`、`docs`、`test` 等）。
- 撰写 RFC 或 PR 模板正文不自动授权推送分支或创建 PR；提交、推送与建 PR 仍以用户明确指令为准。

## 从既往工作归纳的协作习惯

这些是默认偏好，遇到当前指令或仓库惯例不同，应相应调整。

- 用中文沟通分析、进展和交付；代码注释倾向简洁英文，减少模板话术，说明必要的意图或限制。
- 先读真实实现和已有测试，再确认缺口。搜索命中只算线索，需要检查调用和断言；优先复用已有覆盖，避免重复维护。
- 明确验证结论的边界：生成、静态检查、实际执行、覆盖充分性分别说明；单进程工具测试、多卡通信验证、mock 场景各自能证明什么要说清。
- 根据需求选择功能、结构、异常、数值或性能验证，不把旧任务的特定测试限制沿用到新任务。
- 多条需求需要追踪时，保留原始输入，另建可追溯的处理记录；将范围处置、覆盖判断和运行结果分开，跳过或待处理不算通过。
- 对需要复现的结果保留对应命令、源码版本、日志和验证范围；存在多份源码时按需核对提交或文件哈希。安装包的测试结果不能冒充当前源码构建后的验证。
- **Python 环境隔离与项目标识**：在机器上使用或创建 Python 环境时，保证**项目间严格隔离、项目内可识别复用**。动手前先排查环境中是否存在能明确识别为属于当前项目的隔离环境（核实归属、完整性和版本匹配后可复用，便于同项目多个并行 agent 协同）；若无法明确识别为当前项目环境或不可复用，则为当前项目新建带清晰项目标识与归属说明的独立隔离环境，不借用无标识或其他项目的环境，也不原地覆写同项目其他 agent 正在使用的环境。具体建环与恢复细节按 `remote-npu-environment` 执行。
- 倾向把任务分析、临时证据与拟合入仓库的代码分开整理。采用当前目录已有组织方式，不强制固定目录名或报告模板。
- 接续较长任务时维护简短的最新状态入口，写清已完成、未完成及证据位置；旧报告保留为历史，不让旧“下一步”覆盖新结论。
- 提交信息和代码风格参考目标仓库及用户给出的格式；旧任务的提交、推送或改写历史授权不自动延续到新任务。

## 新目录的快速导入

1. 读取当前目录已有的 `AGENTS.md`、README 和交接记忆（如存在），了解新任务和目录约定；无需寻找或复制历史任务目录。
2. 将本 skill 中的身份、仓库辨识和协作习惯载入当前上下文。只核实新任务真正依赖的仓库位置、目标分支、实现版本和验收范围，不为导入背景本身要求用户填写清单。
3. 用户要求初始化目录并保存背景时，按现有记忆约定落盘；无约定时在 `MEMORY.md` 中新增或更新“通用工作背景”小节。仅保存上述可复用背景，与当前任务进度分开；保留文件中其他内容，重复调用不重复追加。仅要求了解背景时无需创建文件。
4. 简短说明已导入的背景，然后继续当前任务。机器连接、账号、依赖安装及环境复现不属于本 skill；需要时使用已安装的 `remote-npu-environment`，其缺失不影响背景导入。

## 记忆维护边界

后续仅将用户确认的长期事实或明确偏好更新到通用背景。单次需求、接口清单、特定跳过规则、测试数量、提交号、分支、仓库绝对路径及执行状态留在各任务记录；不记录机器地址、账号、卡号、环境版本或安装步骤。

不把某次测试生成 skill 的工具选择、断言限制、执行审批流程或命名模板提升为小组统一规范；需要这些细节时读取当前任务实际采用的专项规范。
